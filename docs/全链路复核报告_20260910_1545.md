### 1.1 `Virus_Platform_Core/web/meta.py` — 引擎路径拼接回归（P1，功能完全不可用）

**证据**

```python

cmd = engine_cmd(os.path.join(os.path.dirname(os.path.abspath(__file__)),
```

`__file__` 为 `…/vp/web/meta.py`，`dirname` 得 `…/vp/web`，再拼 `Virus_Platform_Core/public_meta`

**修复**：与 `main.py:cmd_meta_search/cmd_meta_info` 对齐，改用模块对象 `__file__`：

```python
from Virus_Platform_Core.public_meta import search_engine
cmd = engine_cmd(search_engine.__file__, '-q', species, ...)
```

**验证**：`search_engine.__file__` / `info_engine.__file__` 均 `isfile=True`；
`meta` 蓝图可导入；`engine_cmd` 冻结分支只用 `basename`，与 `Virus_Platform_Core/engine_entry.py`
的 `_ENGINES` 映射兼容，打包路径同样成立。

**根因**：`app.py` 拆分到 `Virus_Platform_Core/web/` 那次目录下沉时，手拼路径未同步。
**教训**：子进程跑内部引擎一律 `import + __file__`，不手拼相对路径。

## 3b. 三项 FAIL 已修复（16:07 追加）

用户要求修掉上面 3 项。**复核后发现真凶与初判不同，且 3 项里没有一个是平台代码缺陷。**

### 3b.1 🎯 真凶：宿主会话的 `safe-delete` 守卫劫持子进程退出码

**症状**：批量跑时大量测试 **0.2~1.5s 内 rc=1**，但报告里该测试自身断言
**全部 ok 且末尾有 `...PASSED`**；单跑同一测试 **PASS**；且**越跑越糟**。

**证据链**

1. 单跑 PASS、手工 `subprocess.run` PASS，唯经运行器批量 FAIL → 差异不在测试代码。
2. 读 `tests/_run_all_report.txt` 拿到夹在中间的：
   ```
   [safe-delete][SAFE_DELETE_BULK_CONFIRM_REQUIRED]
   {"count":853,"threshold":50,"targets":[".../run/results/itmsa"]}
   ```
3. 环境变量命中宿主注入：
   `CODEBUDDY_SAFE_DELETE_ENABLED=1`、`..._BULK_THRESHOLD=50`、
   PATH 前置 `<...>/cli/vendor/shim/safe-bin`。
4. **决定性验证**：起子进程时剥掉全部 `CODEBUDDY_*` → `_it_msa` 立刻 rc=0。

**机制**：会话给子进程注入删除守卫，`count` 是本会话**累计删除数**，
一旦 >50（实测已达 970），测试收尾的 `shutil.rmtree(work)` 就被标记
`SAFE_DELETE_BULK_CONFIRM_REQUIRED` 并**把 rc 改成 1** —— 明明断言全过。

**修复**：`tests/_run_all.py` 新增 `_child_env()`，启动子进程时剔除
`SAFE_DELETE*` / `CODEBUDDY_*`，并从 PATH 摘掉 `safe-bin` 段。
（测试只清理平台自己的 `run/` 受控目录，无需外部删除守卫。）

> 口诀：**「断言全 ok 但 rc≠0」先怀疑进程收尾被外部 hook**。
> 抓法：让运行器把 tail 落盘再读，别只看终端。

## 4. 逻辑层复核：管道上下游自洽

### 4.1 拓扑排序 ✔

15 个阶段函数与 `STAGE_REGISTRY` 一一对应；全选时的执行顺序实测等于
`STAGE_ORDER`：

```
subsample → fastp → fq2fa → host → virus → assembly → verify → consensus
→ hostana → orf → orfa → phylo → primer → gbdraw → report
```

未知阶段名有 WARN 日志（`run_analysis` 与 `_stage_execution_order` 双保险），
不会静默丢弃。

### 4.2 断点续跑语义 ✔

- `verify` / `consensus` 硬校验 `03_assembly/viral_contigs.fasta` 存在，
  缺失时抛中文可读错误（非静默）。
- `consensus` 显式用 `01_host_removal`（**非** `02_virus_screen`）取 reads，
  符合"变异/准种检测不经过病毒相似度筛选"的设计意图（已写入 docstring）。
- 可选阶段（fastp / fq2fa / gbdraw / orfa / verify）在工具缺失时静默剔除，
  但**留日志**；`_stage_execution_order` 保持调用方顺序做稳定拓扑。

### 4.3 设计观察（非缺陷，供决策）

`subsample / fastp / fq2fa / host / virus / assembly` 六阶段的 `deps=[]`。

- **原因**：它们各自按固定产物路径读上一阶段输出，顺序由 `STAGE_ORDER` 与
  写入顺序体现，形成隐式依赖。这样换来"任选子集跑"的灵活性。
- **代价**：依赖图不能表达真实数据流——若手选 `['assembly','host']`，
  不会强制 `host` 先跑（但 `assembly` 会因缺产物而报错，属可接受）。
- **若要收紧**：可给这 6 个补线性 deps（`host→virus→assembly` 等），
  代价是丧失"单跑某步"能力。当前 app 侧 `PIPE_TEMPLATES` 已给出正确组合，
  属可接受的工程权衡。

### 4.4 阶段权重与耗时模型 ✔（2026-09-11 更正）

> **更正**：本节原先写"`STAGE_WEIGHTS` 覆盖全部 15 阶段"，实际有两处不实——
> 该表只有 14 项（漏 `subsample`），而且**全仓没有任何读取点**（`_RunState.est`
> 走的是 `_est_stage_sec` → `DEFAULT_STAGE_EST`）。已删除 `STAGE_WEIGHTS`，
> 并把 `subsample` 补进 `DEFAULT_STAGE_EST`（原值靠 `('plain', 60)` 兜底，
> 值与补上后一致）。现由 `tests/_it_stage_tables.py` 用集合不变量守住
> "每张阶段表都覆盖 STAGE_ORDER"。

全局进度占比的唯一真源是 `DEFAULT_STAGE_EST`：区分 `('gb', 秒/GB)` 与
`('plain', 秒)` 两类，`_GB_STAGES` 由前者推导，EMA 更新逻辑
（`_update_stage_perf`）自洽；每个 `STAGE_ORDER` 阶段都必须在此登记，
否则回退 `('plain', 60)` 且 ETA 偏。
