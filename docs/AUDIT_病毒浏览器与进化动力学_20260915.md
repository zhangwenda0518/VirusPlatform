## P0-1 `tools.html:1780` 的多余 `</div>` 摧毁了 DOM 结构

### 现象（实测）

用 chromium 解析 `webapp/templates/tools.html` 原文（`set_content`，不经 Jinja）：

```
main 的直接子元素（20 项，末项即止）:
  NAV#moduleTree, DIV#groupLanding, SECTION#t-convert, ..., SECTION#t-sdt, SECTION#t-rdp

t-rdp        祖先链: SECTION#t-rdp → MAIN → DIV.tools-layout → DIV.page     ← 正常
t-rtt        祖先链: SECTION#t-rtt → DIV → DIV.page                          ← 没有 MAIN
t-phylogeo   祖先链: SECTION#t-phylogeo → DIV → DIV.page                     ← 没有 MAIN

.page 的直接子元素: [DIV.tools-layout, DIV#rdpResult.card, DIV, DIV]
```

模板里 `</main>` 在 **1945 行**，`t-phylogeo` 在 1843–1889 行——本该在 `main` 内，实际跑到了 `main` 外面。

### 影响范围（实测）

全模板共 21 个 `<section class="card" id="t-*">`，只有 **18 个**是 `main` 的直接子元素：

- **脱离 `main` 的 3 张**：`t-rtt`（时间信号）、`t-phylogeo`（系统地理）、`t-dsrna`（dsRNA 设计）
- `#rdpResult`（重组结果卡）也被甩到 `.page` 下

`showModule()`（`tools.html:2042-2054`）用 `main.querySelectorAll(':scope > *')` 切换显示，只处理 **直接子元素**：

```js
main.querySelectorAll(':scope > *').forEach(el => {
  if (el === landing || el === strip) return;
  el.style.display = el.id === id ? '' : 'none';
});
```

→ 点「⏱ 时间信号」或「🌍 系统地理」胶囊时，`main` 内所有 section 被隐藏，而目标卡片不在 `main` 内、不受这段代码控制 → **主工作区空白，卡片错位显示在页面下方**。

### 根因

`</div>` 在 HTML5 里的语义是"**pop 直到弹出一个 div**"（不是"弹一个 div"）。第 1780 行出现时，栈中最近的 div 是 `div.tools-layout`：

```
html > body > div.page > div.tools-layout > main > section#t-rdp
                                                        ↑ 栈顶无 div
1780 的 </div>  →  pop 掉 section#t-rdp、main，最后弹掉 div.tools-layout
```

于是 1780 之后的所有内容都成了 `div.page` 的子元素；`1792` 的 `</section>`、`1945` 的 `</main>` 全部变成多余标签被忽略。

**同一类问题还有一处：第 1838 行**（在 `t-rtt` 卡片内）多余的 `</div>`，作用相同。

标签配平扫描（自写 HTMLParser）的原始输出：

```
- 闭合 div 时跳过了未闭合标签  行1780  [('section','t-rdp',1730)]
- 多余的闭合标签                行1792  section
- 闭合 div 时跳过了未闭合标签  行1838  [('section','t-rtt',1795)]
- 多余的闭合标签                行1840  section
```

### 对照证据：这是本次新增引入的

| 版本 | `<section id="t-*">` 总数 | 在 `main` 直接子元素中的数量 |
|---|---|---|
| `git HEAD`（拆分前） | 17 | **17（全部）** |
| 工作区（当前） | 21 | **18（缺 3）** |

`HEAD` 版结构完整，工作区版缺 3 张 → 破坏由本次新增（`_zz_split_phylodyn.py` 拆分 + 新增 t-dsrna）引入。

### 建议修复方向（未执行）

删掉 `tools.html:1780` 和 `1838` 两处多余的 `</div>`；`1791` / `1839` 的孤立 `<div>` 也一并清掉。改完用同一方法复验：三张卡都应是 `MAIN` 的直接子元素。

## P1-2 `/api/vexplorer/send_to_phylodyn` 忽略请求体里的筛选条件

### 现象（实测）

同一筛选条件 `Family=Potyviridae`，只换传参方式：

| 传参方式 | HTTP | 返回消息 |
|---|---|---|
| **A. `body.args`**（前端未勾选时实际走的分支） | 400 | 均衡抽样后仍有 **39068** 条，超过上限 5000 |
| B. `query string`（对照） | 400 | 均衡抽样后仍有 **9936** 条，超过上限 5000 |

**39068 是"不加任何筛选"的全库均衡抽样结果**（≈1953 个区域 × 20），而 Potyviridae 的正确值是 9936。两者差 4 倍，证明 **A 分支的筛选条件被完全丢弃**。

（两次都返回 400 只是因为我的测试条件命中量本身就超过 5000 上限，与本次 bug 无关；关键是两条路径算出的分母不同。）

### 代码定位

- 前端 `vexplorer.html:391`：未勾选时发 `body = JSON.stringify({ args: Object.fromEntries(p), geo_balance: ... })`，URL **不带** query
- 后端 `vexplorer.py:521`：`df = _apply_filters(ds['df'])`
- `_apply_filters`（`vexplorer.py:239-284`）通篇读 `request.args`，**从不读请求体**：
  ```python
  args = request.args
  ```

对照组 `/api/vexplorer/export` 是正常的——前端把参数拼进 URL（`vexplorer.html:416` `url += '?' + p.toString()`），后端读 `request.args` 能拿到。

### 后果

从 Explorer 点「🧭 导出并送入进化动力学分析」、且未手工勾选任何序列时，**100% 报错**。这是该按钮的主用法（"按筛选条件导出"）。

## P2-5 `rdp5_engine.mask_from_events` 的 `aln_len` 口径错误

### 实测

构造 3 条 × 100 bp 的比对（真实比对长度应为 **100**）：

```
mask_from_events 传给 merge_intervals 的 aln_len = 300      ← 错，应为 100
普通区间 (10,20)  → merged = [(10, 20)]         n_masked = 11
环状区间 (90,10)  → merged = [(1, 10), (90, 300)]   ← 期望 [(1,10),(90,100)]
```

### 代码定位

`rdp5_engine.py:227-231`：

```python
aln_len = 0
with open(fasta_path, ...) as f:
    for line in f:
        if not line.startswith('>'):
            aln_len += len(line.strip())        # ← 累加了「所有」序列的长度
```

应为单条序列长度（如首条或 `max`）。

### 危害

`merge_intervals`（`rdp5_engine.py:155-173`）对 `bp_start > bp_end`（跨末端环状重组）会拆成两段：

```python
else:
    segs.append((b, aln_len))      # ← aln_len 被高估 3 倍
```

→ 返回的 `merged` 是 `[(1,10),(90,300)]` 而非 `[(1,10),(90,100)]`。

**当前被掩盖**：`mask_alignment` 用 `min(e, len(rows[0]))` 兜底裁剪，实际掩蔽的列是对的。但 `mask_from_events` **返回给调用方的 `merged` 区间是错的**，下游若按它写报告或再做处理就会出错。

环状基因组在植物病毒里很常见，这条路径会被真实走到。

### P3-10 bootscan 的窗口位点池不完整 【推断】

`rdp_detect.py:240-249`：

```python
vi = 0
for (mid, _, _) in obs:
    s0 = mid - win_sites // 2
    lst = []
    while vi < len(var_cols) and var_cols[vi] < s0 + win_sites:
        if var_cols[vi] >= s0: lst.append(var_cols[vi])
        vi += 1
```

`vi` 只单调前进，而 `obs` 的窗口按 `step_sites` 滑动（`step < win`，窗口相互重叠）。前一窗消耗掉的列不会回填 → 第 2 个窗口起，`win_vars` 只包含**非重叠区**的列，系统性偏向窗口右侧且数量偏少。

影响：bootstrap 支持度估计有偏。函数注释里已经提到过一次类似的坑（"全列重采样时断点支持度掉到 0.3"），说明这段逻辑对重采样池很敏感。

**建议**：改成按窗口重新过滤 `var_cols`，或对每个窗口二分定位起止下标。**未实测**，是纯逻辑推导。
