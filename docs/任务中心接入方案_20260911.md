## 1. 设计：TaskManager 支持「外部任务」

现状：`/api/tasks` 只返回 `tm.list_all()`，而 `DownloadManager` 自建线程、
自建状态、自建轮询与取消，从不调用 `tm.start` → 任务中心完全看不到下载。

不要在 `DownloadManager` 里反向依赖 `web`（分层会乱，且定时线程里碰
Flask 上下文不安全）。正确做法是给 `TaskManager` 加一层**外部任务挂载**：
执行仍归各子系统，`tm` 只做统一展示与停止转发。

在 `web/tasks.py` 的 `TaskManager` 中新增：

```python
def attach(self, name, provider, on_cancel=None, link=None, key=None):
    """注册「外部任务」：工作由别的子系统执行，本管理器只做统一展示与停止转发。

    provider() -> dict | None，每次快照时调用（在 self.lock 之外）：
        {'status': 'running'|'done'|'failed'|'cancelled',
         'pct': float|None, 'msg': str, 'stage': str, 'error': str,
         'eta': int|None, 'log': [str], 'started': float|None,
         'finished': float|None}
      返回 None 表示任务已消失（从列表移除）。
    key: 稳定标识（同一 key 重复 attach 只登记一次），缺省用 name。

    外部任务不占 heavy/light 并发名额、不落 tasks/*.json（否则重启后会变成
    「幽灵任务」被 _recover_interrupted 误标为失败）。
    """
```

需要改动的 6 处（都很小）：

1. `rec` 增加 `external=True` / `provider` / `on_cancel`；`attach` 里按 `key`
   去重（维护 `self._ext_keys = {}`）。
2. `_persist()`：`if rec.get('external'): return` —— 不落盘。
3. `snapshot()`：先从锁内取出 `rec`，若是 external 则在**锁外**调
   `provider()`，把返回字段映射成现有快照结构（`status` 映射到
   running/done/failed/cancelled 词表，`log` 直接用 provider 给的列表）。
   provider 抛异常 → 记 warning 并当作 `None`（任务消失），不能连带
   `/api/tasks` 整个 500。
4. `list_all()`：先 `_prune_external()`（provider 返回 None 或
   `hidden=True` 的移出 `tasks`/`order`），再照常快照。
5. `cancel()`：external → 调 `on_cancel()`，返回 True/False；不碰 `procs`。
6. `delete()` / `clear_finished()`：external 只置 `rec['hidden']=True`
   （不 pop），否则下次 `attach` 前会「删掉又冒出来」；`_trim_memory()`
   对 external 跳过 `order[_KEEP_TOTAL:]` 的淘汰（它们开销极小且数量有限）。

`full_log()` 对 external 直接返回 `provider()['log']`。

## 2. 下载批次接入（P1-2）

`Virus_Platform_Core/web/download.py` 增加绑定函数，由 `app.py` 在注册
blueprint 后调用一次：

```python
def bind_downloads():
    """把已有与后续下载批次挂进任务中心（外部任务，只读镜像 + 停止转发）。"""
    from Virus_Platform_Core import public_data
    from Virus_Platform_Core.web.tasks import tm
    mgr = public_data.get_manager()

    def _provider(bid):
        s = mgr.snapshot(bid)
        if not s:
            return None                      # 批次已被删除 → 卡片消失
        st = {'resolving': 'running', 'downloading': 'running',
              'converting': 'running', 'completed': 'done',
              'failed': 'failed', 'cancelled': 'cancelled',
              'interrupted': 'failed'}.get(s['status'], 'running')
        return {'status': st, 'pct': s['overall'], 'stage': s['status'],
                'msg': (f"已下载 {fmt(s['done_bytes'])}/{fmt(s['total_bytes'])}"
                        f" · 速度 {fmt(s['speed'])}/s"
                        + (f" · 剩余 {s['eta']}s" if s['eta'] else '')),
                'error': s.get('error') or '',
                'eta': s.get('eta'), 'log': mgr._read_log_tail(bid_batch, 40)}

    def _attach(bid):
        tm.attach(f"下载·{bid}", lambda bid=bid: _provider(bid),
                  on_cancel=lambda bid=bid: mgr.cancel(bid),
                  link='/download?pop=1', key=f'dl:{bid}')

    for b in list(mgr.batches.values()):     # 启动时补挂已有批次
        _attach(b['id'])
    mgr.add_listener(_attach)                # 之后新建的批次自动挂上
```

需要在 `public_data.DownloadManager` 加一个极小的观察者（约 6 行）：

```python
def add_listener(self, fn):
    self._listeners.append(fn)
    for b in list(self.batches.values()):
        fn(b['id'])
```

并在 `create()` 落库后调用 `self._notify(bid)`。

`app.py` 末尾：

```python

```

**做这一步前必须先给 `DownloadManager` 加 `started` / `finished` 时间戳**
（epoch），否则任务卡的「耗时」是空的：`create()` 里 `b['started']=time.time()`，
`_finalize` / `_convert_sras` 收尾时 `b['finished']=time.time()`，`snapshot()`
透出。

前端 `tasks.html` 基本不用改：卡片靠 `task.link` 生成「前往页面」按钮，
`stopTask` 走 `/api/task/<tid>/cancel` → `tm.cancel` → `on_cancel`。

## 3. 批处理队列排队项（P1-4）

`web/samples.py` 的 `SampleQueue` 只在条目**真正开跑**时才 `tm.start`
（`samples.py:145`），`queued` 期间在任务中心完全不可见。用同一机制补：
provider 只对 `status == 'queued'` 的条目返回状态，一旦 `running`/终态就返回
`None`（此时真正的 `队列·<sample>` 任务已经出现，避免同一件事两张卡）。

存储扫描（`web/settings.py` `_do_storage_scan`）同理：在 `_storage['scanning']`
为真期间挂一张 external 卡；扫描结束 provider 返回 `None` 自动消失。
它的触发点在 `api_storage` / `api_storage_rescan`，在那里 `attach` 即可。

### 5.1 `TaskManager.attach`：外部任务挂载

`web/tasks.py` 新增（`Virus_Platform_Core` 侧不反向依赖 web，依赖保持单向）：

```python
tm.attach(name, provider, on_cancel=None, link=None, key=None, weight='light')
tm.detach(key)
```

- `provider() -> dict | None`：每次快照时在**锁外**调用（避免与 provider 内部
  可能的重入互锁）。`None` = 真身已消失 → 卡片移除；抛异常 = 这次读不到 →
  **降级卡片保留**（见 5.3-d）。
- `rec['external']=True`，**不落** `tasks/<tid>.json`（否则重启后被
  `_recover_interrupted` 当成幽灵任务标失败）、**不占** heavy/light 名额。
- `tid = sha1(key)[:12]`（形状与 `uuid4().hex[:12]` 一致，`_tid_ok` /
  前端 `data-tid` 直接可用），同一 `key` 重复 attach **tid 稳定不变**。
- `cancel()` → 转发 `on_cancel()`；`delete()` / `clear_finished()` → 只
  `hidden=True`（真身归各子系统管，pop 掉下次 attach 又复活，像删不掉）；
  `_trim_memory()` 跳过外部任务。

### 5.3 实施中发现并修掉的问题（都不是设计稿里预见到的）

| # | 问题（症状） | 根因 | 修法 |
|---|---|---|---|
| a | `/api/tasks` 出现 `[null]`，任务中心页 JS `list.filter(...)` 直接 TypeError，整页白 | 外部任务的真身在**两次取快照之间**被删除 → provider 变 `None`，而 `list_all()` 先取 id 列表、后逐个 `snapshot()`，收尾没滤掉 `None` | `return [x for x in outs if x]`；并把 `_prune_external()` 提到取快照之前 |
| b | 真身已删的外部任务卡片永远留在列表里清不掉 | `_prune_external` 只认「hidden」，没区分「provider 干净返回 None（真身没了）」与「provider 报错」 | 新增 `_provider_missing()`（异常**不算**消失）→ 明确返回 `None` 才 `_drop_external`（连带清 `_ext_keys`） |
| c | 一次瞬时读失败就让用户的下载卡片**永久消失** | provider 抛异常被当作「任务消失」 | 新增 `_provider_state_ex()` 返回 `(state, ok)` 区分两种 `None`；`ok=False` 时给**降级卡片**「状态读取失败（会自动恢复）」 |
| d | 降级卡片显示「开始 · 耗时 **496971 h**」 | 降级时 provider 没给 `started`，前端把它当 0（epoch） | 降级分支回落到记录里的挂载时间 `started0` |
| e | `bind_downloads()` 第二次调用后卡片全部失效（快照恒为 `None` → 卡片被当「已消失」删掉） | `attach()` 命中已有 key 时**直接 return**，没换 `provider`/`on_cancel` 闭包 —— 一旦执行对象（`DownloadManager` 单例）被重建，卡片仍指向**旧对象** | 命中已有 key 时刷新 `provider`/`on_cancel`/`link`/`name`（tid 与 `started` 保持不变） |
| f | **全局重置会把「已完成」的下载批次改写成「已取消」**（用户会以为数据白下了） | 外部任务的 `rec['status']` 只是**登记初值**，从不随 provider 更新；而 `active_ids()` / `cancel_all()` / 全局重置的收尾等待**只看 `rec['status']`** → 早就跑完的批次永远「运行中」→ 被遍历到并转发取消 | 新增 `_refresh_ext_status()`（provider 结论写回 `rec['status']`，锁外调用），由 `list_all()` 与 `active_ids()` 调用 |
| g | 同上，**第二道防线**：即便有一次误转发，也不能改写终态 | `DownloadManager.cancel()` 无条件 `b['status']='cancelled'` | 新增 `_TERMINAL_BATCH_STATES`（completed/cancelled/failed/interrupted）：终态批次只清理残留子进程、**不改状态**，返回 `False`（前端不会假称「已停止」） |
| h | `api_storage` 存在 `storage→tm` 的锁序隐患 | `_bind_storage_scan()` 被写在 `with _storage_lock:` **块内**，而 `_storage_lock` 是**不可重入**的 `threading.Lock()`，且 provider 快照时会拿它 | 把挂载移出锁块（`started` 标志 + 锁外调用），与 `api_storage_rescan` 的写法一致 |

> 附注（设计约束，别踩）：**不能在 `attach()` 里顺手探一次 provider 来拿真实状态** ——
> `_bind_storage_scan()` 是在持有 `_storage_lock` 时被调用的（见 h），而 storage
> provider 自己也要拿这把不可重入锁，会直接死锁。状态一律只在快照/`active_ids`
> 路径上取。

### 5.4 「只看当前样品」筛选：最终结论

§0 里的分析（默认关闭、勾选后项目级任务会被隐藏）实测无误，最终处理：

1. `webapp/templates/tasks.html: sampleMatches()` **新增第 4 条**：
   认 `排队·<样品>`（以及英文 `Queued·<样品>`）的**镜像卡**。
   理由：那张卡就是属于这个样品的，不认它的话，用户刚入队一个样品、一勾
   「只看当前样品」它就凭空消失。后端 `samples._task_matches_sample`
   **故意不加**这条（注释已写明）：镜像卡不占任何资源，不该让「样品忙」

### 内置 HTTP 回退下载的两处**真实缺陷**（本轮修，`_dl_python`）

这条路径是 aria2c 缺失/失败时的兜底（自定义 URL 条目、NGDC 场景都走它），
此前**零测试覆盖**。补 `tests/_it_dl_http_fallback.py`（本机 HTTP 服务端，
离线）时当场暴露两个 bug：

1. **断点续传会截断已下载的前缀**。续传时发 `Range: bytes=pos-` 拿到的是
   后半段，但代码用 `safe_open(part, 'wb')` 打开 —— **`'wb'` 会截断**，
   于是把"前半段 + 后半段"变成"只有后半段"。实测 1 MiB 文件续传后只剩
   524288 B，**而 `done_bytes` 仍按累计字节数报成完整长度**（进度条 100%、
   文件不完整）。有 `expect_bytes` 时会被完整性检查判 failed（表现为
   "续传永远失败"）；无 `expect_bytes` 时（`db: 'URL'`、部分 NGDC 条目）
   就是**静默交付坏文件**。改为 206 响应时以 `'ab'` 追加。
2. **416 分支是死代码**。`urllib` 的 opener 对非 2xx/3xx 是**先抛
   `HTTPError`**、不会把响应对象交出来，所以写在 `with` 体内的
   `if r.status == 416` 永远不会执行，416 一路掉到 `URLError` 分支被当成
   下载失败 —— "进程在改名之前挂掉、本地 `.aria_part` 其实已完整"这种
   情况**永远收不了尾**。改到 `except urllib.error.HTTPError` 里处理。

新测试还锁定了核心不变式「**磁盘实际大小 == 上报的 done_bytes**」，
以及三道完整性闸门（字节数不一致 / 无精确值偏差过大 / gzip 损坏 → failed）
与精确总量优先（`expect_bytes` 不被 content-length 覆盖）。

### 重启恢复路径：一个坏 batch.json 会拖垮整个下载模块（本轮修）

`DownloadManager._load_all()` 跑在 `DownloadManager()` 构造里、由

### 收尾阶段（.sra 解码）完全无法取消（本轮修）

`.sra → FASTQ` 解码可能跑几分钟（GB 级 .sra），用户在收尾阶段点「停止」
是常见操作。原实现三处叠加导致**取消被静默丢弃**：

1. `for sra in sras:` 循环里**没有任何取消检查** → 剩余 .sra 照样逐个解码；
2. 解码用 `subprocess.run(...)`，**没登记进 `self.procs`** →
   `cancel()` 的 terminate 逻辑找不到它，进程继续吃 CPU；
3. 收尾处 `b['status'] = 'completed' if done or not b['files'] else 'failed'`
   **无条件覆盖** → 用户明明点了停止，批次最后显示「已完成」。

实测（`tests/_it_dl_convert_cancel.py`，离线 7s，慢解码桩）：取消后
**3/3 个 .sra 全被解码、`killed=0`、状态变 completed**。

修法：新增 `_run_decode_cmd()` 用 Popen 并**以批次目录内的键登记进
`self.procs`**（cancel 的前缀匹配才认得出）；循环首部与 except 分支都检查
`cancelled`（被杀掉的那个不算转换失败）；收尾处取消态一律不覆写，并把
`convert_msg` 写成「已取消（未完成的 .sra 可点『重试转换』）」；
`_convert_bz2`（DDBJ 路径）同样加取消检查。
修后实测：进程被终止（`killed=1`）、剩余不再解码、状态保持 `cancelled`、
不误报 ⚠；不取消时行为完全不变（2/2 解码、`.sra` 清理、`ready_files` 可用）。

`astype(str).str.strip().str.lower().isin(_META_NA)` 被重复算 2~3 次。
改法：

1. 一次性算出整表缺失掩码 `na_mask`，各列与 `complete` 复用它；
   `df.iterrows()` 换成 `(~na_mask.any(axis=1)).sum()`（847 ms → 0.5 ms）；
   `filled` 也复用掩码，不再重复调用 `_meta_missing_count(df)`。
2. 叠加整包响应缓存（键 = `name/which/表 mtime`），`?force=1` 绕过
   （页面「🔄 刷新图表」按钮已透传 `force`）。

**等价性证据**：10 个真实项目表（含 15851 行的 Arabidopsis search）
改前抓基线、改后逐字段比对 → **全部逐字节一致**；`summary.complete`
另用独立参照实现交叉验证（15167 = 15167 = 15167）。
**提速**：冷调用 1822 → 999 ms（受机器波动影响，关键项 847 → 0.5 ms），
热调用 **0.6 ms**。

### 顺带修掉的小瑕疵

- `tests/_it_dl_delete.py` **把两条空测试批次永久留在了用户的 `run/downloads`
  里**：① 的 `it_delfiles_test` 是故意留记录验证「列表仍显示该批次」的，跑完

  的前提下打的，预期 400，于是从没真正删过目录）。阶段二把批次接进任务中心
  后，这两条会在任务中心各显示一张「已下载 — / — · 0/2 文件」的卡片，非常
  显眼。测试收尾已补上清理（内存记录 + 目录），并当场清掉了用户环境里的残留。
  **教训**：会写 `PLATFORM_ROOT` 下真实目录的测试，收尾必须自己擦干净。

- `download.html` 的 `fmtBytes` 阈值原是严格 `>`，导致恰好 1 000 000 B
  渲染成「1000 KB」、1e9 B 渲染成「1000.0 MB」，看着像换算错误。改为 `>=`。

  `data-dl-overall` / `data-dl-file` / `data-dl-size-cell`），纯附加属性，

  连跑 4 个 Edge 会话时实测出现过 msedgedriver 原生崩溃（单独复跑即通过），
  属会话级抖动。只对 `WebDriverException` 重试，断言级失败照旧原样返回。
