## 事项 1 · `Virus_Platform_Core/primer.py` 与 `Virus_Platform_Core/primer_design.py` 两套引物栈是否合并

### 现状（三份代码、两条独立链路）

| 文件 | 行数 | 角色 | 调用方 |
|---|---|---|---|
| `Virus_Platform_Core/primer.py` | 247 | 管线/工具链：基于样本目录产物设计，写 `06_primer/primers.tsv` | `pipeline.py:575`（阶段⑧）、`tool_jobs.py:345`（工具页引物卡）、`tool_results.py:984`（单 contig 分析四件套） |
| `Virus_Platform_Core/primer_design.py` | 362 | 交互式单序列设计：输入 FASTA 文本/文件，返回覆盖图 + 表格数据 | `tool_results.py:1064`（`/api/tool/primer_design` ← `/primer` 页 `primer.html:347`） |
| `Virus_Platform_Core/primer_thermo.py` | 293 | 热力学评估（二聚体/发夹/3′端/GC/Tm/探针），**只被 `primer_design.py` 用** | `primer_design.py:24` |

### 两套参数与输出口径实测对比

同一条序列（`example_contig_1`，6096 bp）、同一 primer3 版本（2.3.0）：

```
A) Virus_Platform_Core/primer.py   产物区间 [[300,1500]]  温度 57-63℃  GC 40-60%
   输出字段: name, F_seq, F_pos, F_len, F_tm, F_gc, R_seq, R_pos, R_len,

     primer3.bindings.designPrimers（每次调用发 UserWarning）

B) Virus_Platform_Core/primer_design.py（PCR）
   summary: n_pairs=5 best_score=82.2 avg_score=66.2 n_recommended=1 n_usable=4
   首对: F=CGCGCGCAGTTAGCTAAAAT Tm=60.0 GC=50.0 product=939
         score=64.4 USABLE

   → 0-100 分 + RECOMMENDED/USABLE/NOT_RECOMMENDED + 探针 + 覆盖图坐标
     (amp_start/amp_end/amplicon_span) + 盐浓度/dNTP/DNA 浓度等进阶层参数

**结论**：同一条序列经两个入口得到**不可比的结论**——A 只给"penalty 0.062 / self_dimer 32.6"这类原始字段，不告诉你"这对引物能不能用"；B 给分数与等级。用户从「工具页引物卡」和「/primer 页」拿到的质量判据不同。

### 可选方案

| 方案 | 做法 | 代价 | 风险 |
|---|---|---|---|
| **A. 统一引擎（推荐）** | `primer.design_primers_for_seq()` 内部转发到 `primer_design.design_for_sequence()`；`primers.tsv` 增列 `score`/`recommendation`；`designPrimers` → `design_primers` | 约 60-80 行改动，2 个文件 | 低。产物文件名/路径不变，只在末尾加 2 列；`primers.tsv` 的既有列全部保留 |
| B. 只补评分列 | 在 `primer.py` 里 import `primer_thermo` 补算分数 | 约 20 行 | 低，但**两套 primer3 参数仍然并存**，同序列仍可能给出不同引物集 |
| C. 彻底合并 | `primer_design.py` 吸收 `primer.py`，只留一个模块 | 300+ 行 + 动 `pipeline.py` 阶段契约 | 中。`06_primer/` 产物契约与 3 个调用方都要回归 |
| D. 维持现状 | 什么都不做 | 0 | 长期两套参数各自演化，报告与页面口径继续分叉 |

**我的建议：A**。它把"引擎"统一（新接口 + 热力学评分 + 探针能力），同时不动管线产物契约——`primers.tsv` 只是**多两列**，`pipeline.py`、工具页、单 contig 分析三处调用方零改动。C 的收益不比 A 多多少，但回归面大得多。

### 实施结果 ✅

- **`Virus_Platform_Core/primer.py`**：删除自持的 `P3_GLOBAL`，只保留管线特有的
  `PIPELINE_PRODUCT_RANGE = (300, 1500)`；`design_primers_for_seq()` 转发到
  `primer_design.design_for_sequence()`，**保持全部历史字段名**
  （`F_seq/F_pos/F_len/F_tm/F_gc`、`R_*`、`product`、`penalty`、
  `self_any_max`、`hairpin_max`），新增 `score`、`recommendation`、
  `probe_seq/probe_tm/probe_gc`、`amp_start/amp_end`。
- 自二聚体/发夹列沿用 primer3 口径（负 Tm 钳到 0）→ **列语义不变**。
- `primers.tsv` 增列 `score`、`recommendation`（现 17 列）。
- 工具页引物结果表新增「质量评分」列（中英双语 `tk.thQuality`）。

**等价性验证**（`tests/_verify_primer_merge.py`，逐字段对拍旧路径）：

```

> 已实施：**A 植物口径白名单过滤**（`ictv_db.acvirus_acc_index()` → 6,195 条）

### 它们怎么进参考池的

`Virus_Platform_Core/phylo.py:604-610` 把整个 ICTV VMR（`ictv_db.load_taxa()`，**全病毒界** 20,179 accession）并进 `ref_tax`；当 ③ 没有 `virus_classification.tsv`（`assembly.py:425` 明确允许的降级态）时，`cls_map` 为空 → 走到 `ref_ids` 兜底，按 accession 从 `gb_refs.fa` 提取。

### 实测后果

```
34 条序列 / 最长 41kb / 合计 966 kb 的比对：
  MAFFT 跑 20 分钟仍无输出（O(L²) 的 DP 在 40kb×40kb 上爆炸）
对照（合成数据，同一台机同一 MAFFT）：
  8 条 × 6.4kb  →  3.0 s
  20 条 × 6.4kb →  3.8 s
  8 条 × 40kb   →  28.0 s
```
即：**序列条数不是问题，单条长度才是**。植物病毒基因组通常 3-13kb（Closteroviridae 最长约 20kb），40kb 的参考几乎必然是误入。

### 现成的植物口径名单（关键）

平台**已经有**植物口径的 accession 白名单，无需新建：

```

databases/tax/ictv/acvirus_accs_ictv.txt   20,179 行（全病毒界）
抽查：AF440571 / EU545650 / AM087120 / MH447526  → 均 **不在** plant 名单里
databases/tree_db/plant_virus.fasta         27.7 MB（48 科 / 6,167 条植物病毒）
```

### 可选方案

| 方案 | 做法 | 代价 | 效果 |
|---|---|---|---|
| **A. 植物口径过滤（推荐）** | 参考池只收 `acvirus_accs_plant.txt` / `plant_tree.db` 覆盖的 accession（`ictv_db.DEFAULT_ACV_DB = 'plant'` 本来就是默认口径） | 约 15 行（`phylo.py` 组 ref_tax 处加一个集合过滤） | 直接消除误入；对植物样品无损 |
| B. 长度上限 | 参考序列 > N kb（建议 25kb）时跳过并记 WARN | 约 10 行 | 防未来再混入超长序列，但不解决"宿主不相关" |
| C. 长度带匹配 | 只选长度在 contig 长度 ±3× 区间内的参考 | 约 25 行 + 需要先扫一遍参考长度 | 更精细，但要额外 I/O 扫描 |
| D. 现状（已加的缓解） | 已有 ① MAFFT 体量降级（>100 条或 >500kb 时转 `--retree 2 --maxiterate 0`）② 参考按 `_ref_pref`（RefSeq/完整基因组）优选排序 | 0 | 仍可能选中 40kb 序列，只是慢得"可预期" |

**我的建议：A + B**。A 用现成名单零成本、根因解决；B 当护栏（阈值 25kb，超限跳过并写日志）。C 收益增量小、复杂度高，可以不做。

### 实施结果 ✅

1. **A · 植物口径过滤**（`Virus_Platform_Core/phylo.py` 组 `ref_tax` 处）：ICTV VMR 部分只收
   `ictv_db.acvirus_acc_index()`（默认 `DEFAULT_ACV_DB='plant'`，6,195 条）内的
   accession；植物参考库（`virus_ref`）本身即植物口径，全部保留。
   名单不可用时退化为不过滤并记 WARN。
2. **B · 长度护栏**（`MAX_REF_LEN = 25000`）：`_extract_refs()` 新增
   `max_len` 参数，超限参考跳过并记 PLAN 日志；返回
   `(found, skipped_long)`，`skipped_long` 会被排除在 `not_found` 之外——
   否则会为 40kb 古菌病毒白跑一次 NCBI 下载。
3. **连带修复 · 兜底选参改为"本地可用优先"**：实施 A 后实测只剩 **1 条**参考
   （比修复前的 30 条还糟）。原因是上一轮我加 `_ref_pref` 排序时，其
   `(RefSeq, 完整基因组)` 大量并列，并列时按 accession **倒序**排，恰好挑中
   字母靠后、本地没有的 accession；于是选出 30 个 id 却只提到 1 条序列。
   现在先用 `_scan_ref_accessions()` 扫描参考源里**真有的** accession
   （只读 `>` 头行，31MB 约 0.5s），再在可用集合内按 `_ref_pref` 排序。

### 顺带修复：`detect_tools()` 漏掉"已随包"的工具 ✅

`detect_tools()` 原先只覆盖 25 个工具，而 `tools/` 里还有若干工具
（samtools / salmon / table2asn / bcftools / pandepth / viral_consensus）
不在探测表里——源码模式靠 `platform.json` 手填的绝对路径才能用，而打包版
用的是**干净配置**（`tools: {}`），于是这些"已经随包"的工具在发布版里探测不到：

```
修复前  源码模式 28 个工具 → 27 ✔（缺 iqtree2）
        打包模式 25 个工具 → 24 ✔（少了 salmon / samtools / table2asn）
```

**修复**：给 `detect_tools()` 补上这 6 个工具的候选路径
（`tools/samtools/bin/samtools.exe`、`tools/salmon2/salmon.exe`、
`tools/table2asn/table2asn.exe`、`tools/bcftools/bin/bcftools.exe`、
`tools/pandepth/pandepth.exe`、`tools/viral_consensus/viral_consensus.exe`）。

snpEff（jar）与 SNPGenie（perl 脚本）**刻意不放进探测表**——它们不是可直接
执行的单文件工具，由 `known_virus_suite` 自己按
`tools/snpeff/snpEff/snpEff.jar`、`tools/snpgenie/snpgenie.pl` 定位。

**验证（打包 exe 实测）**：

```
VirusPlatform.exe --cli tools → 31 个工具，仅缺 iqtree2（本机确实未安装）
  salmon       ✔ tools\salmon2\salmon.exe
  samtools     ✔ tools\samtools\bin\samtools.exe
  table2asn    ✔ tools\table2asn\table2asn.exe
  bcftools / pandepth / viral_consensus  ✔
```

**顺带验证了"目标机没装 gbdraw"的路径**：以最小 PATH 启动打包 exe 后，
`gbdraw` 解析为 `bundled:gbdraw`（进程内引擎），图谱预览仍返回
19,533 字节的 SVG —— 说明发布版不依赖目标机安装 gbdraw。
