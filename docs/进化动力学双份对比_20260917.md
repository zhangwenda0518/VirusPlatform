## 0. 一句话结论

> **两边不是同一份内容，是两套独立实现，谁也不包含谁。**
>
> - **A 的进化动力学** = 新写的 `phylodyn_kit.py` + `phylodyn_trees.py`（合计 **2,359 行**），
>   拆成 **13 张独立小卡**（`t-pdprep` … `t-pdmjrm`），走「工具箱」路线。
> - **B 的进化动力学** = 新写的 `phylodyn_local.py`（**1,711 行**）**+ 10 个专用引擎模块**
>   （`treetime_ml` / `rtt_drt` / `bsp` / `mjrm` / `mot` / `treedater` / `beast_io` /
>   `beast_handoff` / `geo_subsampler` / `phylogeo`），走「阶段流水线 A0→A5 + 轨道 A/B」路线。
> - 两边**唯一同源的东西是 `phylogeo.py`**：A 是 09-16 16:03 的**裁剪快照**，B 是**持续演进版**。
>   同名的 60 个函数里 51 个逐字相同、9 个 B 带修复而 A 没有、B 还多 20 个函数。
> - 全库**同名函数只有 6 个**（且全是 `_read_table`/`_walk`/`find_rscript` 这类小工具）——
>   说明 A 的 kit/trees 和 B 的引擎是**各写各的**，不存在"同一份代码的两份拷贝"。

**合并可行性**：i18n 命名空间 `tk.pd*` 两边**只有 1 个键重名（`tk.pdH2`），且取值完全相同** →
UI 文案层几乎零冲突。真正的冲突全在**后端算法口径**（见第 5 节）。

## 3. 架构差异：工具箱 vs 流水线

```
A（植物病毒分析平台）—— 13 张各自为战的卡
  t-pdprep  t-pdrename  t-pdgroup  t-pdspacetime  t-pdsub
  t-pdrand  t-pdrrt  t-pdtempmig  t-pdbsp  t-pdrspp
  t-pdtreetime  t-pdltt  t-pdmjrm
  ＋旧 3 张：t-rdp  t-rtt  t-phylogeo
  ※ 卡与卡之间靠用户手工搬文件；没有「一条链跑完」的入口

B（植物病毒进化分析平台）—— 1 条阶段流水线 + 9 张卡，且分轨
  轨道 A（本机、不跑 MCMC）
    t-phylodyn  A0 数据准备 → A1 时间推断 → A2 地理迁移
                → A3 群体动态 → A4 祖先序列 → A5 汇总溯源
                （接口产物固定为 clock/timetree.nwk；支持单阶段/续跑）
    t-rtt       RTT + DRT
    t-phylogeo  Fitch + RRT 置换 + 坐标弧线图 + 打包给服务器
    t-treedater 真 treedater + LTT
    t-rdp       RDP5
  轨道 B（需服务器 BEAST）
    t-mjrm  t-bsp  t-mot  t-beast
  compare 组：t-idprep（ID 对齐与分组 + 可选降采样）
```

**这不是"同一功能的两种排版"，而是两种设计哲学。** B 的
`docs/模块设计_时间与地理推断_20260917.md` §2.4 明确把 A 那种做法列为"结构性问题"：

> 1. 卡片式而非流水线式 —— 8 张卡各自为战，中间产物靠人工搬运，没有"跑完一条链"的入口
> 2. 时间与地理之间没有明确的接口产物
> 3. BEAST 依赖与本地能力混在同一组 —— 用户从卡片列表看不出哪 4 张必须交服务器

A 的 16 张卡正是这三条的**放大版**（13 + 3，且无轨道标记）。

## 4. 逐能力对照矩阵

图例：**同** = 同源/等价；**异** = 两边各写一套；**仅 A** / **仅 B** = 单边独有。

## 5. ★ 会算出不同数字的地方（口径冲突清单）

这一节是合并时**最需要小心**的部分：同一个科学问题，两个平台会给不同的数。

| 科学问题 | A 给什么 | B 给什么 | 能不能比 |
|---|---|---|---|
| **"有没有时间信号？"** | `R² ≥ 0.5` 硬阈值 `strong_signal` | DRT 日期随机化检验的经验 p 值（阈值 0.05） | ❌ 判据不同源。B 文档实测 R² 硬阈值小样本误判率：8 叶 23.3% / 12 叶 3.3% / 20 叶 1.7% |
| **"换了几次区？"** | TempMig 分支-年矩阵：**每条分支对跨越的每个日历年 +1**，状态取 MCC 树 **MAP 注解** | A2：`corridors.tsv` 里 **`ml`（TreeTime ML 点估计）与 `fitch`（最少变化数）并列两列** | ❌ 不是同一统计量。A 的数还受"年 × 方向"分解影响；B 明确写"两列不可相加、不可互替" |
| **"根在哪？有多确定？"** | `RSPP-Viz`：读 BEAST 根注解的**贝叶斯后验**（`K.set`/`max.set`） | `rssp_bootstrap`：**对可比对列重抽样 + Fitch** 的 bootstrap 支持率；A2 另给 TreeTime **ML 边际概率** | ❌ 三种量。B 的代码注释专门警告"ML 边际概率 ≠ 贝叶斯后验" |
| **"松弛钟速率多少？"** | `trees.treedater_ltt`（自研 R 调用） | `treedater.py`（真 treedater，含 CoV/parboot） | ⚠️ 同一个 R 包，但调用口径/参数集不同，结果需实测对拍 |
| **"LTT 斜率多少？"** | 自研：log N 对时间线性回归 | treedater `parboot` 的真 LTT | ❌ A 文档自己写了"只是净多样化的近似，不冒充 treedater" |
| **"Ne(t) 长什么样？"** | 只画你给的 Tracer TSV / BEAST log；log 口径的组界按**等区间数 × 逐样本根高**近似 | A3：TreeTime `--coalescent skyline` 直接估 Ne(t)；`bsp.py` 另给每段 ESS | ❌ 前者是绘图/近似，后者是模型估计 |
| **"转移矩阵年轴"** | `mostcurrentyear` = **第二大叶年**（复刻 VirPhyKit 抗极端新近样本口径） | `mot.py` 有独立的**时间标度自检** | ⚠️ 年轴定义不同 |
| **"降采样抽了哪几条"** | `seed` 留空 → **不可复现**（`random.Random(None)`） | `seed` 留空 → 固定 `20260915`，可复现 | ❌ A 默认跑两次结果不同 |

**唯一会天然一致的数字**：两边 `region_permutation_test` 的 p 值（函数逐字相同，
`p = (1 + #{零分布 ≤ 实测}) / (N + 1)`，双尾 `p_low`/`p_high` 都给）。但前提是
喂进去的 **tip 区划标注一致** —— 而标注来自 `_header_traits`/`match_states_and_years`，
**这两个函数两边已经不一样了**，所以实际也可能不同。

## 7. 合并建议

### 方案一：B 为基线（推荐）★

**做法**：以 **B 的进化动力学为骨架**（它更新、更完整、有全链编排与轨道分区），
把 **A 独有的三块**补进去：

1. **数据接入四来源**（A 的 `t-pdprep`）→ 作为 `A0 prep` 的**前置卡**接进 B。
   B 的 A0 只吃"已经准备好的比对 FASTA + 元数据"，A 的 pdprep 正好补上
   "从 explorer 导出包 / 粘贴 / GenBank 拿到 FASTA+元数据"这一段。
2. **VirSpaceTime 时空分布绘图**（A 的 `t-pdspacetime`）→ 直接搬，B 没有对等物。
3. **VirPhyKit 精确对拍口径**（A 的 `t-pdtempmig` TempMig、`t-pdmjrm` XML 插入）→
   如果目标是"与 VirPhyKit Example 逐格/逐字节一致"，A 这两张卡的实现是有 Test 证据的
   （107 年 × 25 方向零差异 / 逐字节一致），可以保留为**"VirPhyKit 对齐模式"**的独立卡，
   与 B 的 `mot.py`/`mjrm.py` **并列**（不要试图合成一个函数，它们回答不同问题）。

**为什么推荐**：
- B 的 `phylogeo.py` 是 A 的**严格超集**（+20 函数、6 处修复），B 为基线 = 免费拿到修复；
- B 有 A 完全没有的：全链编排、ASR、同塑性、免 MCMC skyline、BEAST 导入/交接、ESS 诊断、
  import-export、轨道分区 —— 这些是**净增量**，反向（A 为基线）等于把它们全丢；
- B 的 i18n 只有 36 个 `tk.pd*` 键、A 有 209 个，**从 B 出发加卡比从 A 出发拆卡容易**；
- 搬运量小：A 侧真正独有的只有 `phylodyn_kit.py` 的接入/时空绘图/MJRM 部分，
  约 400–500 行可独立摘出。

**风险**：B 是**未纳入 git** 的工作区（A 有 `.git`，B 没有）——
合并前**先给 B 建 git 或全量快照**，否则出错无回退。

### 方案二：A 为基线

把 B 的 `phylodyn_local.py` + 8 个引擎模块搬进 A，做成第 14 张卡。

- 优点：A 有 git、有 3rd/R、是"主平台"（用户主要在这个平台上工作）。
- 缺点：要搬 **~8,600 行**引擎代码 + 8 个 handler + 1 张大卡 + i18n + 轨道分区；
  而且必须**同时把 A 的 `phylogeo.py` 换成 B 的版本**，否则搬运过来的功能会踩 A 的旧 bug。
  换 `phylogeo.py` 又会连带影响 A 现有的 `t-rtt`/`t-phylogeo`/`t-pdtempmig` 行为 —— 需回归。
- 结论：**可以，但工作量与回归面都比方案一大一个量级。**

### 方案三：不合并，只做"口径对齐 + 交叉指引"

保留两份，但：
1. 把 A 的 `phylogeo.py` 升级到 B 的版本（**强烈建议，无论合不合并**）；
2. 两侧页面上互相标注"同一个科学问题在对面是哪个卡、口径差在哪"；
3. A 侧修掉 `t-pdsub` 默认不可复现（给个固定默认种子）。

适合"两边服务不同用户群、短期不合并"的情况。

### 无论选哪个方案，这 5 件事必须先做

1. **把 A 的 `phylogeo.py` 同步到 B 的版本**（或至少补上 `_header_traits` /
   `resolve_years` / `parse_newick` / `_node` 这 4 处修复）。
   这是**现在的实际风险**：A 上跑 VirPhyKit 命名的数据集会整片判未命中，月日级采样会被压成整年。
2. **给 B 建版本控制**（B 无 `.git`，所有改动只靠 `.bak_*`）。
3. **清理 A 的死代码**：`tools.html` 里 `takePrefill('phylodyn')` 与 `t-phylodyn` 相关残留注释；
   `pages.py` 里那段"LTT / skyline 仍只在进化平台"的过期注释。
4. **A 的 `t-pdsub` 默认种子**：从 `None` 改成固定值（建议对齐 B 的 `20260915`）。
5. **合并后跑一遍跨平台一致性对拍**：同一份数据，A 的 `t-pdtreetime` vs B 的 `t-rtt`，
   A 的 `t-pdbsp` vs B 的 `t-bsp`，A 的 `t-pdrspp` vs B 的 `rssp_bootstrap` ——
   数字不同是**预期**的（口径不同），但要**逐条确认差异来源**，不能"看起来差不多"就过。
